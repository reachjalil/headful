# Headful adaptation boundaries

Headful retains the T3 Code application and server rather than wrapping a separate scaffold. The existing desktop lifecycle starts one backend and stops it on Quit. A scoped Headful Effect service in that backend owns the local Salesforce store, CLI adapter, org context, reviewed workflows and the mod host. Desktop and contributed MCP transports call that same service. Desktop IPC validates the installed application sender; its authorization is an exact-body signature from a capability held in native memory, never in a file or renderer code. The backend removes that capability from its environment before starting Salesforce CLI or provider subprocesses. MCP clients receive their own revocable, org-scoped grants. Neither an mod nor a model call can approve a provider write.

The public Salesforce workspace renderer, pure contracts, bounded REST operations, and exact reviewed user/access/permission workflows were deliberately adapted from the author's existing Headful Cloud implementation. Cloud-specific account sessions, OAuth applications, vault keys, production configuration and private coordination material were not transferred. Temporary public/local and private/cloud persistence adapters share the same originating workflow algorithm; consolidation should extract pure operation decisions without coupling portable contracts to either runtime.

Salesforce CLI retains Salesforce authentication and refresh tokens. The public utility Mod calls approved CLI commands with validated argument arrays, structured JSON, bounded output and execution, cancellation, and an explicit verified org/principal target. Its narrow operations include record inspection, SOQL, object descriptions, limits, jobs, and logs; there is no arbitrary CLI or Apex capability. Existing reviewed workflows retain their bounded REST service with short-lived provider access kept server-side. Ordinary metadata and durable workflows live in an owner-only SQLite store. Headful client grants are hashed in an owner-only grant store; separately generated owner-only bridge credential files contain only Headful grants. They can be revoked without changing Salesforce authentication.

Feature registry decisions apply in service dispatch and MCP discovery as well as navigation. Disabling an org or feature blocks new operations. An in-flight provider write cannot honestly be described as cancelled; its durable receipt or unknown outcome remains available for review.

Every packaged application includes its shared native workspace and the compiled public utility Mod. Builds with the optional proprietary agent Mod also include local MCP App HTML/CSS/JavaScript and its stdio helper. No desktop product asset or Salesforce request depends on Headful Cloud. Generic MCP clients get structured and text results. Host rendering and fullscreen capabilities are feature detected; native-host acceptance is separate from protocol and fixture checks.

`apps/mobile` and shared T3 client foundations remain intact. Desktop packaging remains Mac-only. The optional compiled Connect Mod supplies authenticated outbound remote transport and a minimal private controlled-client development journey; there is no native mobile distribution or unauthenticated remote Salesforce endpoint. It shares the authoritative Salesforce runtime, with separate per-org remote opt-in and non-human grant authority.

## Salesforce request and cache contract

All native REST, onboarding and principal-verification requests use `apps/server/src/headful/SalesforceHttp.ts`. This adapter uses the runtime's native fetch and connection reuse, without a second HTTP client or a custom global dispatcher. Requests reject redirects, bypass HTTP response caches, preserve conditional write headers with `Headers`, enforce runtime-owned authorization, and combine caller cancellation with a 20-second deadline covering the response body. Bodies are consumed or cancelled and bounded to 4 MiB (100,000 bytes for onboarding queries and 200,000 for userinfo).

Typed domain services enforce client, feature and org authority before requesting an explicit saved target. Paths are versioned Salesforce data resources, with no arbitrary URLs, dot segments or anonymous Apex. Mutating methods must enter the reviewed-write boundary. The internal `write` flag classifies uncertainty; it does not approve an operation.

Concurrent read-only verification of the same username on one CLI adapter shares only an in-progress lookup. Each consumer checks its saved org, principal and instance origin. The lookup is removed on success or failure, and writes get independent fresh verification. The license inventory uses one verified session for the duration of that read operation: describe plus three parallel inventory queries share the exact token and a 20-second provider deadline. The read callback cannot dispatch mutations or remain usable after completion. A subsequent operation verifies again, so changing a CLI login cannot retarget an active inventory or carry stale identity into the next one. Permission/unsupported-resource failures can yield partial categories; network failures, cancellation, expired auth and invalid data fail the operation. After confirming a parent permission set, its independent object and field inventories run concurrently. CRM record reads, stale-state checks and provider readback remain fresh.

The runtime requires Salesforce CLI 2.136.0 or newer and retrieves access tokens with `org auth show-access-token --json`, pinned to the username resolved by `org display`. Standard display output is metadata, and redacted credentials are rejected. Refresh tokens and SFDX auth URLs are never requested; raw credential output remains native and is not returned to clients or logs. [Salesforce CLI credential change](https://github.com/forcedotcom/cli/issues/3560).

Pre-dispatch cancellation sends nothing. Read HTTP 408, 429 and 5xx are provider-unavailable failures rather than permission failures or empty successful inventories. After a write is dispatched, cancellation, timeout, incomplete/oversized responses, HTTP 408 and 5xx leave an unknown outcome requiring reconciliation. HTTP 412 requires new review. The HTTP adapter never retries writes or refreshes credentials itself; Salesforce CLI owns authentication.

Provider conditional response caches require an exact target/principal/revision/version/request key and a matching stored body for 304 responses. No provider response cache is enabled. Salesforce's documented ETag support is for Account rows; time-based validators cover rows and describes, not generic SOQL queries. [Salesforce conditional requests](https://developer.salesforce.com/docs/platform/api-rest/guide/intro-rest-conditional-requests.html).

Metadata discovery and suggested retrieve commands pin API version 67.0. Component lists include the exact type/folder scope, provider-returned count and an explicit completeness limitation; a display cap or empty list cannot prove absence, dependency safety or mutability. Folder-based types require an exact case-sensitive folder, and advertised types are checked before listing. Metadata API, source tracking and package-format coverage differ. [Salesforce CLI metadata discovery](https://developer.salesforce.com/docs/platform/salesforce-cli-reference/guide/cli_reference_org_list_metadata.html), [metadata coverage](https://developer.salesforce.com/docs/success/metadata-coverage-report/references/coverage-report/metadata-coverage-report.html).
